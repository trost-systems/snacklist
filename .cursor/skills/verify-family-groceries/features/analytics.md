# Analytics and error tracking

After the first sign-in on a device, before onboarding or the list, the app asks once whether it may store a random install id on the device and send pseudonymous usage data and error reports to PostHog (EU); the text names Peter Trost as the one asking and links the privacy policy. Both answers are one tap. With a yes it sends `first_open`, then events such as add, tick, household created, invite sent or accepted and category or store reorder, never an item name or other list text; with a no it sends nothing, ever. A yes counts only for the consent text version it was given under; after a new text the app asks again. Mehr → Nutzungsdaten switches it on or off for the device; off stops sending at once and deletes the install id. The install id exists only after a yes. Internal users (debug builds, test accounts, the server's tester group `internal`; job 337 removed the long press) are filtered out of the gate insights; debug builds and the group `internal` also see "Testfehler senden" under the version line. Edge functions report their exceptions, tagged with the function name. Background and definitions: `docs/ANALYTICS.md`.

## Sub-features

- `an-consent` the consent screen (`analytics-consent`, app bar title "Nutzungsdaten" with a logout icon (tooltip "Abmelden"), heading "Darf Snacklist Nutzungsdaten erfassen?", buttons `analytics-consent-decline` "Nicht erlauben" and `analytics-consent-accept` "Erlauben", equal weight, no draft mark (text approved 2026-11-01, consent text version 2026-11-10 since the Snacklist name, job 174), the link "Datenschutzerklärung" (`analytics-consent-privacy`) to https://snacklist.app/datenschutz, English https://snacklist.app/en/privacy) right after the first sign-in on a device, route `/analytics-consent`; an invite link keeps its code through it; an MCP authorization tab is not interrupted.
- `an-decline` after "Nicht erlauben" nothing reaches the PostHog host, also after adding and ticking.
- `an-events` after "Erlauben": exactly one `first_open` per device, then `household_created` (`store_count`, `default_stores`) / `invite_accepted` (method `link` or `code`), `item_added` (source `typed`, `spoken`, `suggestion`), `item_ticked` once per tick (undo sends nothing: a put-back from "Zuletzt verwendet" within 10 minutes of the tick is no `item_added`), `category_reordered` (scope `default` or `store`), `store_reordered`, `item_categorized` (`via`), `invite_sent` (`channel`, `context`), `dedupe_hint_shown` / `_merged` / `_ignored`, `paywall_viewed`, `feedback_submitted`; each with `household_id`, none with list text. The full allow-list is `eventCatalog` in `app/lib/analytics/events.dart`.
- `an-version` every decision is stored with the consent text version (`analytics.consent_text_version` in the device cache, `analytics_consents.consent_text_version` on the server). A yes under another version or none counts as no decision: at the next start the app deletes the install id and the SDK's data, sends no event (flags only through the no-consent request, `an-flags`) and asks again. A no stays a no.
- `an-server` each install's answer is recorded on the server (`record_analytics_consent`), so server events (`item_added` from the server, `siri_add`, `siri_read`, `integration_blocked`, `purchase_*`; `serverEventCatalog` in `supabase/functions/_shared/telemetry.ts`) go out only after a yes to the current version. Proved by `e2e/tests/alexa.spec.ts` "the app records each install's analytics answer for server events (AC10)".
- `an-switch` Mehr → Nutzungsdaten (`more-usage-data` → `more-usage-data-page`, route `/more/usage-data`, job 85): the switch "Nutzungsdaten und Fehlerberichte senden" (`more-analytics`) shows the decision and changes it; off is one tap, stops sending at once and deletes the install id. On asks first (Legal N-298, job 317): a bottom sheet (`analytics-consent-sheet`) with the consent question, privacy link and both buttons; only `analytics-consent-accept` turns it on (new install id, `first_open`), `analytics-consent-decline` or closing the sheet (tap outside, Escape, system back) leaves it off and decides nothing. The hint under it is "Gilt für dieses Gerät. Ausschalten löscht die Kennung auf diesem Gerät.". Proved in `app/test/analytics/more_toggle_test.dart` and `e2e/tests/analytics.spec.ts` "after a no, the switch asks the consent question again; only Erlauben turns it on (Legal N-298)".
- `an-install-id` the install id (`analytics.install_id` in the device cache; `analytics.install_id` in the web's localStorage too) is absent before the answer and after a no, made at the yes, deleted when switched off, and new after switching on again. An id an older build stored without a yes, or one kept under a yes to an older consent text, is deleted at the next start. Proved in `e2e/tests/analytics.spec.ts` (localStorage) and `app/test/analytics/analytics_test.dart`.
- `an-internal` a debug or profile build, or a user in the server's tester group `internal` (`public.tester_groups`, job 337), sees the "Testfehler senden" button (a test account or the RevenueCat tester household is internal for analytics but sees no button in a release build) (`more-test-error`) below `more-version`; there is no long press and no `more-internal` line any more. `select public.my_tester_groups()` as the user lists the groups; `fg db query "insert into public.tester_groups (user_id, group_name) select id, 'beta-de' from auth.users where email = 'peter@fg.test'"` adds one (service role only).
- `an-errors` an uncaught app error and an edge-function exception arrive in PostHog error tracking, scrubbed.
- `an-sdk` (job 44) the app runs posthog_flutter (posthog-js on the web) only after the yes: before it no request reaches the PostHog host and posthog-js is not even fetched; off closes the SDK and deletes its files (ids, queue). Only allow-listed keys leave a browser.
- `an-flags` (job 44, job 257) `Analytics.flags.isOn(key)`: after the yes what the SDK's `/flags` served the install id; without one (not asked, a no, an outdated yes) what PostHog serves the shared id `no-consent` (`PostHogClient.sharedFlags`, one plain `POST /flags/?v=2` without the SDK, cached in `analytics.shared_flags`); off in builds without a key. Proved in `app/test/analytics/flags_test.dart` and by the `/flags` requests in the collector log.

## How to get to it (user POV)

- Sign in on a new device (or a fresh browser profile): the question comes before "Haushalt anlegen" or the list.
- Mehr → Nutzungsdaten → "Nutzungsdaten und Fehlerberichte senden".
- Mehr → hold the version line at the bottom.

## Driving it with fg

Preconditions:

- `fg` builds have no PostHog key by default, so analytics is off there: no consent screen, no Nutzungsdaten row on Mehr, nothing sent. `fg login` goes straight to the list as before. The web e2e build (`app/config/e2e.json`) has a stand-in key and host `https://posthog.invalid`, which the spec answers with a fake collector.
- With `FG_POSTHOG_HOST=http://127.0.0.1:<port>` (job 44) `fg up` builds the app with a stand-in key and that host, which must be on this machine. Start the collector first: `deno run --allow-net=127.0.0.1 --allow-write cli/posthog_collector.ts <port> <out.jsonl> [flag=true ...]`. Every request lands in `<out.jsonl>` (gzip decoded); `/flags` answers the flags given. `fg login` then stops on the consent screen (it times out waiting for the list: tap `analytics-consent-accept` or `-decline`). `fg up` clears the app's data, so the consent is asked again after each `fg up`.

- **`an-sdk`, `an-events`, `an-errors`, native (Linux).** `FG_POSTHOG_HOST` as above, collector running. Login screen and consent screen: `<out.jsonl>` holds only `POST /flags/` with `distinct_id: "no-consent"` (job 257). Accept, add an item at once (`fg type --input Hafermilch --key add-item-field --submit`, then `fg tap --text Schließen`; `fg back` there closes the Linux window), tick it: one `POST /flags/` at the yes, then about 30 s later one `POST /batch/` with `first_open`, `item_added`, `item_categorized`, `item_ticked`, each with our context (`install_id`, `household_id`, `platform: linux`, `is_internal: true`) next to the SDK's `$app_*`, `$os_*`, `$screen_*`, `$session_id`. An uncaught error (a failed `fg marionette -- scroll-to` raises one in the debug harness) arrives as `$exception` with a scrubbed value such as `Bad state: <w> not <w> after <n> <w>`. Open `more-usage-data` (`fg marionette -- scroll-to --key more-usage-data`, `fg tap --key more-usage-data`, `fg wait --key more-usage-data-page`), switch `more-analytics` off, add and tick again, wait 45 s: no new line, and the SDK's folder `~/.cache/fg/<prefix>/clients/<client>/data/com.snacklist.app/posthog/phc_fg_local_collector` is gone (fg gives each client its own data directory). - **`an-consent`, `an-decline`, `an-events`, `an-switch`, web.** Run `scripts/ci-e2e.sh --spec tests/analytics.spec.ts` (GitHub Actions; with Docker also `scripts/gates/e2e.sh --workers=1 tests/analytics.spec.ts`, which takes `/tmp/fg-e2e.lock` itself; never wrap it in `flock`). ## Gotchas

- The build fingerprint includes the PostHog defines: clients built with `FG_POSTHOG_HOST` show as stale in `fg doctor` (`<client>.build: running …, checkout is …`) from a shell without it, and a plain `fg up` rebuilds them without analytics. Keep the variable set for as long as you drive that build.
- The consent decision belongs to the device (browser profile), not the account: a second sign-in in the same Playwright context is not asked again, a new context is. Specs answer it through `signUp` or `answerConsent`.
- posthog-js sends every 3 s, the native and Linux SDKs every 30 s (or at 20 events); "nothing was sent" needs a wait past that (the spec waits 7 s on the web, the Linux recipe 45 s).
- posthog-js drops events from user agents that look like bots unless `opt_out_useragent_filter` is set (the app sets it): a headless browser otherwise sends nothing after the yes.
- The analytics question and the MCP consent page both have a button "Erlauben"; they never show together, but match it with `exact` and check the route (`/analytics-consent` vs `/oauth/consent`).
- Chromium runs the wasm build (job 28): its error frames name Dart functions without lines. The source-map proof above needs the JS build, which is what `--source-maps` and Safari use.
- Never send proof events without `is_internal` (the proofs set it through the `fg.test` user and `ANALYTICS_INTERNAL=true`).
