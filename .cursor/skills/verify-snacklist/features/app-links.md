# Links into the app (app.snacklist.app, app.hummlist.com, snacklist.app guides)

A link to `https://app.snacklist.app/<path>` or `https://app.hummlist.com/<path>` opens that screen of Snacklist: in the installed iPhone or Android app when there is one, otherwise in the web app, with the same result. The paths are the list (`/list`), the add sheet (`/add`), one store's section (`/stores/<store id>`), the More tab (`/more`) and its pages (`/more/invites`, `/more/settings` and the others), invites (`/join/<code>`) and, since job 462, the code entry (`/join`), Liste → Anpassen (`/edit`, `/edit/<store id|none>`), Verlauf (`/history`, `/history/trip/<id>`), a trip's summary (`/trip/<id>`) and one more household (`/households/new`, `/households/new/invite`). Any other path opens the list. Signed out, the link waits through sign-in (and, for an account without a household, through onboarding) and then opens its screen. On snacklist.app only the guides are claimed (`/de/anleitungen`, `/de/anleitungen/<slug>`, `/en/guides`, `/en/guides/<slug>`): the app shows them in its own guide page. The one table of claimed paths is `app/lib/core/deep_links.dart` (`appLinks`, per host group); `docs/DEEP_LINKS.md` explains it.

## Sub-features

- `al-list` `/list` opens the list; the address becomes `/`.
- `al-add` `/add` opens the list with the add sheet open (group „Hinzufügen“ / "Add") and the field „Was brauchst du?“ / "What do you need?" focused; the address becomes `/`.
- `al-store` `/stores/<store id>` opens the list scrolled so that store's divider („<Store>, N Artikel“) is in view, unfolded if it was folded (the fold is then off for good, as after a tap). An id the household does not have, or a store without open items, opens the list as it is. On a start whose saved copy of the list lacks the store (its items came while the app was closed), the list waits for the first answer from the server and decides then; with no answer (offline, server errors) it stays as it is.
- `al-more` `/more`, `/more/invites` („Einladungen“), `/more/settings` („Einstellungen“), `/more/settings/language`, `/more/access` („Zugänge“), `/more/account` („Konto“), `/more/lifetime` (Premium page), `/more/usage-data` („Nutzungsdaten“; its row in Mehr shows only in builds with an analytics key), `/more/household` (the full household page; More has no row for it, nor for `/more/invites`: both open by link only) and `/more/tips` („Tipps“) open that page of the More tab; back goes to More. `/more/feedback` and `/more/feedback/<id>` open „Feedback & Ideen“ and one note; signed out they wait at `/login?next=%2Fmore%2Ffeedback` like the others (driven 2026-11-16 on c2183ca6). `/more/legal` (a former page) lands on `/more`; `/more/join` (More's join page until job 206) on `/join` for a member of a household (both driven 2026-11-14); without a household it goes through „Willkommen bei Snacklist“ like any link (`/welcome?next=/more/join`, from code).
- `al-join` `/join/<code>` opens the join screen with the code in the phone apps. On the web it is the static join page (job 169b W2, household-invites `join-page`): who invites to which household, and „Im Browser beitreten“, which opens the app at `/?invite=<code>` and so the join screen (`link-join`).
- `al-unknown` any other path, signed in, opens the list. Signed out it opens the start screen of the guided start (`/start`, feature onboarding) without carrying the path, as `/` does. (Signed in, `/settings` opens Zugänge and `/your-name` is the name step while it is due (display-name); neither is an app link, so signed out they are dropped.)
- `al-screens` (job 462) `/edit`, `/edit/<store id|none>`, `/join`, `/history`, `/history/trip/<id>` and `/trip/<id>` signed out wait at `/login?next=<path>` like the More pages and open their screen after sign-in; without a household they ride along onboarding (`/welcome?next=<path>`), except `/join`, which opens the code entry at once. `/history`, `/trip/<id>` and `/history/trip/<id>` then open the list while `grocery-log` and `trip-mode` are off (off for everyone, 2026-11-22). `/households/new` and `/households/new/invite` are claimed for the apps but never carried: signed out they open the start screen (`/start`), without a household Willkommen, since the guided start sets the first household up (from `app/test/shell/router_test.dart`, not driven).
- `al-signed-out` signed out, a link above opens „Anmelden“ with `?next=<path>` in the address (an invite, `/?invite=<code>` on the web, instead gives `/login?invite=<code>`, which survives an app kill); after sign-in (and the usage-data question on a new device) the link's screen opens.
- `al-no-household` an account without a household goes through the name step (`/your-name?next=<path>`), „Willkommen bei Snacklist“ and creating or joining a household, with `?next=` in the address on every step of the guided start („Mit wem“ to „Was fehlt gerade?“, then the setup), and then lands on the link's screen. The invite step is not skipped, only put off: the next time the list opens (the „Liste“ tab, or `/`), the guided start's „Jemanden einladen“ („Schritt 7 von 7“, `/start/invite`) shows first (driven 2026-11-14: sign-up from `/more/settings`, „Haushalt erstellen“, Überspringen, Weiter, Überspringen, Weiter, landed on `/more/settings`, then „Liste“ went to `/start/invite`).
- `al-sign-out` signing out never carries the current page: „Abmelden“, the last row of Mehr, ends on plain `/login` (not the start screen).
- `al-root-signed-out` signed out, `/` (and any path that is no app link) opens the start screen `/start` with „Los geht's“ and „Ich habe schon ein Konto“; with a guided start under way on the device, its step (`/start/<step>`).
- `al-guides` (job 462) `/de/anleitungen`, `/en/guides` (a language's guide list) and `/de/anleitungen/<slug>`, `/en/guides/<slug>` (one guide) show the guide in the app's own page, in the language of the address, not the app's: title, headings, paragraphs with bold, italic, code and links, lists, quotes, code blocks and tables (on a phone each table row is a card with its column names). The page loads `https://snacklist.app/data/guides/<de|en>/<slug or index>.json`, which the site build writes. Guides are public: signed out, without a household or before the usage-data question they show as they are, with no detour. A guide opened by a link has ✕ (`guide-close`), which goes to `/` and so to wherever the app would start (the list, or `/start` signed out); opened from the list or another guide it has back. Links in a guide: another guide opens in the app above it, `#…` scrolls to that heading, anything else (Datenschutz, claude.ai, …) opens in the system browser. While loading a spinner (`guide-loading`); offline or a server error: „Die Anleitung konnte nicht geladen werden. Bist du online?“ / "The guide could not be loaded. Are you online?" with „Erneut versuchen“ / "Try again" (`guide-failed`); a guide the site no longer has: „Diese Anleitung gibt es nicht mehr.“ / "This guide no longer exists." with „Alle Anleitungen“ / "All guides" (`guide-missing`). A slug with capitals or other characters the site never writes opens the list of guides. Screen names `guides` and `guide`, never the slug. From `app/test/guides/` and the router tests.
- `al-handoff` (job 462, Decision C) where a link stays in the phone's browser although the app is installed (Safari after a long press, a messenger's own browser), the join page and the site's guide pages offer „In der App öffnen“: on iOS `com.snacklist.app://open<path>`, on Android an `intent://` for the same https link. The app routes `com.snacklist.app://open/<path>` exactly like `https://app.snacklist.app/<path>` (`/join/<code>` signed out: `/login?invite=<code>`); `com.snacklist.app://login-callback?code=…` stays the sign-in's return and is no link (router and app-links tests; the pages' side belongs to the site and the join page).
- `al-apps` on the iPhone and Android apps the same paths open the app instead of the browser (universal links, App Links), and on snacklist.app the guide paths. `/`, the sign-in pages, onboarding, the MCP consent page and, on snacklist.app, everything but the guides (landing, legal, support, changelog) always stay in the browser. Each host group has its own verified intent filter on Android, since Android pairs every host of a filter with every path of it. The app host serves its association file at `/.well-known/apple-app-site-association` and at `/apple-app-site-association` (the same JSON, no redirect); the site's files are `site/public/.well-known/`. A store build is needed for the new paths and for snacklist.app (`applinks:snacklist.app`, the new filters); older builds open only the paths they had.

## How to get to it (user POV)

- Tap an app.snacklist.app or app.hummlist.com link in an email, a message or a web page (for example the onboarding email's link to „Einladungen“).
- In a browser: type or paste the address.

## Driving it with Playwright

Preconditions:

- Baseline household signed in (`signIn` in `helpers/lib.mjs`) for the signed-in recipes; a fresh browser context for the signed-out ones. For the store recipe add a store and tag an item first: `const mia = member(inst, 'mia'); const api = await apiAs(inst, mia); await api.rpc('add_store', { p_household: mia.householdId, p_name: 'Supermarkt' })`, then `.from('items').update({ store_id }).eq('name', 'Nudeln')`; store ids come from `.from('stores').select('id, name')`.

- **Add sheet.** `page.goto('/add')`. Observable: URL ends in `/`, `addSheet(page, L)` visible, `addField(page, L)` focused (the `helpers/lib.mjs` versions take the labels).
- **Store.** Fold Supermarkt with `storeDivider(page, 'Supermarkt').click()`, then `page.goto('/stores/<supermarkt id>')`. Observable: URL `/`, `storeDivider(page, 'Supermarkt')` in the viewport, its items visible again.
- **More page.** `page.goto('/more/invites')`. Observable: URL stays `/more/invites`, button „Neue Einladung“ visible; „Zurück“ goes to `/more`.
- **Unknown.** `page.goto('/does/not/exist')`. Observable: URL `/`, the add field visible, no add sheet. The same for `page.goto('/history')` on a plain launch (no „Verlauf“ tab).
- **Signed out.** In a fresh context `page.goto('/more/invites')`. Observable: URL `/login?next=/more/invites` (the same for `/more/household`: `/login?next=/more/household`, driven 2026-11-09). Sign in with „Weiter mit E-Mail“, „E-Mail“, „Passwort“, „Anmelden“, answer the usage-data question (`answerConsent`): URL `/more/invites`.
- **Without a household.** `signUp(page, email, '/more/settings')`: URL `/your-name` with `next` holding `/more/settings` (type a name, „Weiter“), then `/welcome?next=/more/settings` (the e2e build has no name step and goes there at once); „Haushalt erstellen“, then on the guided start „Überspringen“ (Mit wem), „Weiter“ (name), „Überspringen“ (stores), „Weiter“ („Was fehlt gerade?“), each step's URL carrying `?next=`. `e2e/tests/deep-links.spec.ts` ("a signed-out link survives onboarding for a new account") expects `/more/settings` at the end.
- **Signed out at `/`.** Fresh context, `page.goto('/')` or `page.goto('/does/not/exist')`. Observable: URL `/start`, button „Los geht's“.
- **Guide.** Signed out or in, `page.goto('/de/anleitungen/siri-kurzbefehl')`. Observable: the guide's title „Snacklist per Siri: Kurzbefehl einrichten“ as a heading, ✕ top left; ✕ goes to `/` (signed out `/start`). Until the site serving `/data/guides/` is live, route `https://snacklist.app/data/guides/**` to the files of a local `site/dist/data/guides/` (`node site/build.mjs`).
- **Specs.** `e2e/tests/deep-links.spec.ts`; router cases in `app/test/shell/router_test.dart` and `app/test/shell/app_links_test.dart`; the guide page in `app/test/guides/`; the domain files (both hosts) in `app/test/core/deep_links_config_test.dart`. Run with `scripts/verify.sh --only e2e -- tests/deep-links.spec.ts`.

## Gotchas

- `VH_FLAGS_FULL=0` builds the flag-off screens the e2e specs see: `/history` and `/trip/<id>` open the list (as on the users' build), `/more/feedback` lands on `/more`, More has the household and „Leute einladen“ rows, no name step.
- `page.goto` reloads the web app, as a tapped link does. Wait for the target screen before the next `goto`.
- `al-apps` cannot be driven on a box without simulators. The domain files are checked by `deep_links_config_test.dart`, the live ones by `node e2e/web-smoke.mjs https://app.snacklist.app` (or `https://app.hummlist.com`). app.hummlist.com serves the new association file since the store upload of 6 Nov (`docs/DEEP_LINKS.md`, "Rollout"). Since the Snacklist test uploads of 10 Nov both hosts' files list `com.snacklist.app` and `com.hummlist.app` (assetlinks and AASA read on 2026-11-11). web-smoke itself stops earlier, at `/join/ABC123`: it still expects the Flutter index there, but since 169b that path is the static join page, so read the association files with `curl` instead. Whether iOS picked it up and the new paths open the iPhone app is unverified on a device.
- Both hosts serve the `release` branch, which moves to main with every TestFlight and Play internal upload; since the uploads of 6 Nov it has job 66 (#188). The web app there and test builds from 6 Nov on route every path here. There is no public store release yet (`releases/releases.json`); a phone app built before 6 Nov opens the plain list for `/list`, `/add` and `/stores/<id>`. The recipes here prove main's web build.
- A sign-in that leaves the phone app (magic link, Apple on Android) keeps the link only while the app stays in memory; after the app is killed it opens the list. Invites survive (`link-join`).
- `/settings` (without `/more`) is the old address of Zugänge and Konto; it still works but does not open the phone app.
