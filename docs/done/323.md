## What happens today when a typed item is already there

I read the code for this, and the round page states it.
- **Same name, brand and details as an open item** (case, spaces and umlauts folded): nothing is added. The sheet says "Pasta is already on the list" with no button (`addParsed` → `AlreadyOnList`, list_cubit.dart:760). The server's `items_skip_duplicate` trigger would skip it as well.
- **Same `canonical_key`** (plural, other spelling, synonym), or the same name where only one of the two items has a brand or details: the item is added first. Then "… is already on the list" with **Merge** takes the added note's place until the next letter is typed (`similarItems`, `DedupeHint`). With the sheet closed it shows as a 6 s snackbar.
- **Merge** keeps the older item's name, category, store and price, and deletes the new item. Amounts add up by `merge_quantities`: none + none = 2, 2 + none = 3, but 1 kg + none stays 1 kg. Brand and details come from the older item, else from the new one. Undo follows the merge.
- **Ticked items never match.** Typing Eggs adds a new row, and the ticked Eggs stay ticked.

## Peter's clarification (t1077u, 07:32 CET)

A match shows only inside the sheet, as a suggestion marked apart from one that adds a new item, and the same goes for ticking off. The row on the list behind the sheet is never moved into view or highlighted. The first draft broke this rule in two places, and both were reworked before the PR:
- its AM2 selected the existing item, honey behind the sheet;
- every option put a matched item behind the sheet after an outcome.

Now:
- an outcome leaves the list behind the sheet alone, and the sheet says what happened with the app's own sentences;
- `verify.mjs` checks every frame for both rules.
