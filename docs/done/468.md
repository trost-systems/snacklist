# Job 468: iOS push via FCM and APNs on TestFlight

## Root cause

The client and signing setup was not what stopped notifications. The TestFlight phone holds a
valid production token, and FCM accepted the one notification the server sent during the test
window. After that, production sent nothing: at 10:41 CET (26 Nov 2026) both server switches
went off and their cron jobs were removed, three minutes after the only send.

Production, `select`s only, counts only (26 Nov 2026, about 16:20 CET). The session was not
read-only: the pooler ignored the `PGOPTIONS='-c default_transaction_read_only=on'` that was
set (checked in review 1, `show default_transaction_read_only` reads `off`). For a guarded
read, make `-c "set default_transaction_read_only = on"` the first command of the same psql
call.

| What | Value |
| --- | --- |
| `push_tokens` | 1 row, `ios`, created 10:05 CET, registered again 10:31 CET |
| `net._http_response`, `push` answers | 1: `200 {"status":"sent","devices":1,"sent":1,"failed":0,"removed":0}` at 10:38 CET |
| `cron.job_run_details`, `push_add_flush` | each minute 10:35 to 10:41 CET, then none |
| `app_switches` | `push_household_add` and `push_shopping_day` both **false**, changed 10:41:13 CET |
| `cron.job` | no `push-household-add`, no `shopping-day-reminder` |

pg_net keeps about 6 hours of answers, so earlier sends are not visible. FCM answered 200 with
`failed: 0`, so it took the message: the function counts every message FCM did not take as
`failed`. Which error a wrong-environment token would bring is not documented in
[FCM's error codes](https://firebase.google.com/docs/reference/fcm/rest/v1/ErrorCode) (a
missing APNs credential for the token's environment is `THIRD_PARTY_AUTH_ERROR`, which the
function counts as `failed` without removing the token). `failed: 0` rules out every refusal
either way. Whether the phone showed the 10:38 notification is not known.
If the app was open at that moment, iOS did not show it: the app does not present
notifications in the foreground (docs/PUSH.md, "The app").

The server switches are not this job's to flip (the brief says to leave them on, and
`releases/flags.json` holds them off until Legal's enable GO). This is in NEEDS_LEAD.

## Built

- `app/lib/push/firebase_push.dart`: `_autoInitOn` turns auto-init on and, on iOS, waits for
  the APNs token. `token()` and, on iOS, `deleteToken()` both use it. `deleteToken` then turns
  auto-init off and deletes.
- Review 0 fix: `token()` waits for a `deleteToken()` still running after its caller's timeout,
  so the late delete cannot take the token registered after it. A third test in
  `firebase_push_test.dart` reproduces that: APNs after 3.5 s, the delete abandoned at 3 s, then
  `token()`. It fails without the wait: `deleteToken` lands after `getToken`.
- `app/test/push/firebase_push_test.dart`: drives `FirebasePush` through firebase_messaging's
  real Dart side, with the native channel faked the way 17.1.0 behaves (no APNs token while
  auto-init is off). The delete test fails on main with `apns-token-not-set`. The token test
  fails when the wait before `getToken` is removed.
- `app/ios/Runner/Info.plist`: the `remote-notification` background mode.
- `scripts/ios-push-entitlements.py` with fixture tests (`-test.py`, in the lint gate). It runs
  in `fastlane ios beta` on the exported IPA before upload or validation.
- `app/test/push/push_native_config_test.dart`: pins the background mode and the lane's check.
- `docs/PUSH.md`, "Native".

## Verification

- `flutter test test/push`: 58 passed. Without the fix, the delete test fails with
  `[firebase_messaging/apns-token-not-set]`. With the APNs wait dropped from `token()`, the
  token test fails the same way.
- `python3 scripts/ios-push-entitlements-test.py`: 5 passed. They cover production, a
  development signature, no push entitlement, an unsigned binary and a missing background mode.
- The check has not read a real signed IPA yet: there is no Mac or IPA on the runner, and
  release runs keep no IPA. The first real run is the next release run on main. If it reports
  anything but `production`, that run stops before the upload and opens the "Internal release
  failed" issue. That would be the finding this job could not make from here.
- No device test. The TestFlight retest is below.
