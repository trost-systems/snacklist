# Job 458: hill-climb ticking, unticking and the undo

A tap that ticks a row, and its undo from „Zuletzt verwendet“, now cost a third to a half of the
UI-isolate time they cost on main. Nothing users see changed: the same rows, the same motion, the
same device copy, the same writes.

## What changed

- `ListSnapshot.encode` (`app/lib/list/list_cache.dart`) keeps the joined text of the rows per rows
  list, and `ListCubit._rowsOf` passes one rows list per server state. A save while only the queue
  changed (a tick, its undo, taps offline) joins no row again.
- `ListCubit.tick` (`app/lib/list/list_cubit.dart`) saves nothing when the tap's save
  (`willTick`, job 222) already wrote that queue in that order: its op was the first promised
  tick, the tap saved it, and no debounced save is due. Otherwise it saves as before.

Why the tap was slow: making the device copy's text was 92 % of a tick on main (13.9 of 15.0 ms
at 3000 items). A tap saved twice, and each save joined every row's text again, 1.9 MB at 3000
items.

## The climb

`docs/hillclimb/hc-tick-untick.md` has the frozen metric, the baseline, each step and the result.
3 steps: 2 kept, 1 reverted (one `StringBuffer` for the whole text was slower in AOT than
`List.join`). Decision log: `~/groceries-ops/jobs/458-hc-tick-untick/decision.tsv`.

  8 of 8 pass on main and on the branch.
- Four tests in `list_cubit_test.dart` ("a tick whose row still closes (job 222)" group, job 458):
  the closed row saves nothing new; rows closing out of order save the queue in its new order; a
  tap made before the device copy was read still gets its tick saved when the row closes; a
  partner's add while the row closes is saved with the tick. The first two pin one save per tap
  (main saves a second, identical copy). The third fails if the skip ignores whether the tap saved.
