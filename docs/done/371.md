## What was built

- `scripts/iap/beta-lifetime.ts`: the ops script. It reads the confirmed, non-anonymous accounts
  created before the cut-off from the hosted database (Management API), reads each account's
  RevenueCat state, grants `premium` until 2100-01-01 on the account's own customer where it is
  missing, and asks the purchases function to store it (reconcile). Dry run by default, `--apply`
  to grant, `--created-before <ISO>` for the cut-off (a dry run defaults to now; `--apply` requires the flag,
  job 371b, Legal Review N-347). It is idempotent by state:
  done accounts are skipped and failures are counted, so a rerun converges. It prints counts
  only. Tests: `scripts/iap/beta-lifetime_test.ts` (in the functions gate).
- App: `FreeUnlock` in `app/lib/purchases/entitlements.dart` says whose free unlock premium comes
  from. An account's own grant for good shows the new beta-lifetime line and body on the Premium
  page. A household's grant keeps Legal's N-70 tester and beta lines. Two new ARB keys, drafts.
- Server: no change. `supabase/tests/beta_lifetime.test.sql` (25 checks) proves that a
  promotional grant to 2100 on a user works like a bought Lifetime: `user_has_premium`, API and
  MCP open under `integration_lock` in every household, the same household cap of 20, and a
  re-sync that changes nothing.
- Analytics: no metric counts a grant as a sale (no purchase event). `metrics_test.ts` "a free
  grant is no sale". Beta accounts stay internal (DECISIONS 371.7).
- Runbook: `docs/PAYWALL_RELEASE.md` 5.3a (dry run, apply right before `premium_offer` and again
  right after it, both with the public-launch cut-off fixed in advance; job 371b), 6.1 and 6.2 rewritten, and a rule never to revoke beta household
  grants. `docs/PURCHASES.md` "Beta accounts (job 371)".
- Verify skill: `journeys/premium-beta-lifetime.mjs`, the `prem-beta-lifetime` entry in
  `features/premium.md`, and the FEATURES-FOR-WRITERS section.
