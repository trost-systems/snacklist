# Job 451: perf ports from the hill-climbs #268, #271 and #270

**Status: PR open, DO NOT MERGE (Peter's pick, t1305u).** Two steps of #268 and #271 are ported onto
current `main` with no change users can see. #270 and three of #271's steps stay out (below). #268,
#270 and #271 stay open and untouched.

**Where each port reaches users (review 0).** #271's open-name counts run on every server write in
the build users have: each realtime row, delete and ack. #268's index speeds `suggestUsuals`, and
on the current feature set the add sheet does not call it. `on-device-catalog` and
`input-stable-rows` are `rollout: full` (`releases/flags.json`), so `AddSheetCubit` ranks every key
through `_ranked` -> `suggestEntries`, online and offline. `suggestUsuals` runs only through
`_local`/`_offline`. That happens while those flags are off, which is a new install before
PostHog's first flag answer (every flag is off until then). It also happens when `suggestEntries`
throws, as `_ranked`'s fallback. So #268's numbers below apply to those cases only.

## What is ported

1. **`suggestUsuals` ranks through an index (#268, job 131).** This is the add sheet's ranking with the
   flags off, and its fallback (see above).
   `suggestUsuals` in `app/lib/list/model.dart` keeps one index per usuals list: each folded name and
   each word start, sorted, so what starts with the typed text is one range. The index is kept while
   the same `Usual` objects come back (each keystroke ranks the same list again). When fewer than
   `limit` usuals rank 0 to 2, it falls back to a scan that stops checking a usual once `limit`
   better ones are found. `suggestionMatch` finds word starts without splitting, and the edit distance
   reuses two `Int32List` rows. The ranking itself (`public.suggest_match`'s ranks 0 to 4, then the
   server's order) is unchanged: `suggestionMatch` with its default `below: 5` returns what it did.
2. **A server write checks the open names by counting (#271 attempt 2, job 130).** `ListCubit`
   reloads the usuals when the set of open names changes. On `main` every server write built that
   set twice, over the whole list. The cubit now keeps a count per open name and, for a write that
   names its rows (a realtime row, a delete, an ack), updates only those. A write that names no rows
   (the cache load, a resync) or any write it cannot match recounts the whole list, which is
   `main`'s comparison.

The harnesses: `tool/hillclimb/hc-suggest-cpu/measure.sh` (#268's, with the frozen 5,000-usual
fixture in `app/test/list/suggest_fixture/` and the bench renamed
`app/test/hillclimb/suggest_usuals_bench_test.dart`, since `main` has a `suggest_bench_test.dart` for
the catalog), and `tool/hillclimb/hc-list-cpu/bench.sh` (#271's `measure.sh`, renamed: `main`'s
`measure.sh` there is job 221's Linux probe) with `app/benchmark/list_cpu/`, whose cache stand-in
now saves with `ListSnapshot.encode()` as `main`'s device cache does. Both take CI's Flutter through
`scripts/lib.sh`. New: `tool/hillclimb/lib-ab.sh <base-ref> <pairs> <measure>` alternates a measure
on `app/lib` from the base ref and from HEAD, everything else from HEAD, in a worktree under `/tmp`.

## Numbers (before: `main`, after: this branch)

hz, x86, 12 cores, Flutter 3.50.0, `flutter test` (JIT), every run under `/tmp/fg-hc-measure.lock`,
pairs alternating `main` and branch (`lib-ab.sh`). `main` moved during the runs (86b46eb7a,
b56693e2c, f3c88b848); `model.dart`, `list_cubit.dart` and `list_cache.dart` are the same in all
three. Other jobs kept the 1-minute load at 10 to 35, so only the large moves count. Raw lines:
`docs/done/451/*.jsonl`.

**`suggestUsuals`, p50 of 40 queries x 30 rounds, ms (`hc-suggest-cpu/measure.sh`)**

| Usuals | main (3 runs) | branch (3 runs) | median |
| --- | --- | --- | --- |
| 5,000 (the fixture) | 25.17, 22.02, 22.91 | 0.039, 0.038, 0.035 | 22.9 -> 0.038 |
| 200 (`HC_SUGGEST_USUALS=200`, the most `fetchUsuals` loads) | 0.863, 0.824, 0.850 | 0.084, 0.077, 0.076 | 0.85 -> 0.077 |

Rank mismatches against `expected.json`: 0 in all 12 runs. The cost: the first call on new `Usual`
objects builds the index. At 200 usuals, `cold_p50_ms` was 0.82 to 0.90 ms on `main` and 0.92 to
1.05 ms on the branch in these runs. Review 0's two pairs, at load 27 to 34, gave 0.82 and 0.86 ms
against 4.46 and 1.99 ms. So the first ranking after a usuals reload pays somewhere from 0.1 to
3.6 ms more. The median is over only 30 samples and the load was high, so the range is noisy. It
matters only where `suggestUsuals` runs at all (flags off, or the fallback). At 5,000 the first call
was 19.9 to 24.5 ms on `main` and 17.4 to 26.4 ms on the branch (no clear difference).

**List bench, 8,000 items (3,000 open), p50 ms (`hc-list-cpu/bench.sh`)**

| Bench | main | branch |
| --- | --- | --- |
| `sync_batch` (300 realtime rows) | 416.8, 492.9, 690.0 | 73.6, 116.0, 126.9 |
| `suggest` (400 usuals) | 19.2, 26.4, 35.1 | 5.9, 5.6, 6.1 |
| score (geomean of 11 benches) | 8.56, 10.24, 16.14 | 7.27, 9.15, 11.71 |

Every pair is better on both benches the port speeds up. The other nine move with the load in both
directions (`tick_batch` 529 to 1,183 ms on `main`, 593 to 920 on the branch). Of them only
`resync` and `cache_load` run changed code: a server write that names no rows, which recounts the
whole list like `main` (resync 2.6, 3.4, 3.6 ms on `main` against 1.7, 2.8, 4.0 on the branch). Every bench's `work` value (what
it computed) is identical in all six runs.

**Job 221's Linux profile probe (`hc-list-cpu/measure.sh`) did not run.** It builds a Linux
profile app, and hz has no clang, GTK headers or pkg-config (no sudo to add them); job 221 ran it on
the box. It times ticks with their save, the list's derivations and the snapshot encode. Of these the
port touches only what follows a server write (the ack of a tick), which goes through the same
per-row counting `sync_batch` times. The bench's `tick_batch` never acks (its first send waits), so it
runs none of the changed code, and its moves above are the load.

**List bench at household size, 1,300 items (300 open, 1,000 bought), p50 ms**
(`HC130_OPEN=300 HC130_BOUGHT=1000 hc-list-cpu/bench.sh`; 300 open is job 221's household):

| Bench | main | branch |
| --- | --- | --- |
| `sync_batch` (300 realtime rows) | 34.3, 35.1, 33.7 | 15.2, 16.7, 20.5 |
| `suggest` (400 usuals; flag-off path only) | 14.5, 14.3, 14.9 | 1.19, 2.11, 1.14 |
| score (geomean of 11 benches) | 1.347, 1.347, 1.350 | 1.051, 1.390, 1.191 |

Load 7.5 to 9.5. Every `sync_batch` pair is better: per realtime row about 114 µs on `main` against
51 to 68 µs on the branch, so about 50 to 60 µs saved per row. That is real but far below a frame
(16 ms), so users won't notice it on one row. It adds up in a burst, such as the other phone ticking
many items at once. The score's second pair is worse: `cache_save` and `cache_load` spiked in that
run (2.8 and 32.0 ms against 1.6 to 1.9 and 10.4 to 10.9 elsewhere). Neither runs changed code
apart from the cache load's one full recount, which equals `main`'s. Every bench's `work` value is
identical in all six runs.

What these numbers are not: a phone, the web build (where the index's sort and `Int32List` run as
JavaScript) or a release (AOT) build.

## Behaviour kept, and the tests that hold it

- `app/test/list/suggest_ranking_test.dart`: the top 5 of all 40 queries against `expected.json`, a
  sha256 of the full ranking, and limits 1 to 20. It passes on `main`'s unported code too (checked):
  the expected file is what `main` ranks.
- `app/test/list/suggest_differential_test.dart`: random catalogs and queries ranked by the index
  and by the plain scan in the test.
- Mutants: dropping the index's dedupe, or finding word starts with `contains(' ' + typed)`, fails
  those tests. Raising the scan's cut-off by one rank survives: it only checks more usuals, and
  `take(limit)` gives the same list.
- `app/test/list/list_cubit_test.dart`, "realtime rows refresh them only when the open names
  change" (#271's test): passes on `main` and on the branch. Mutants (no fast path, no decrement of
  the old row, an ack naming no rows) fail it or the existing "they refresh once the list settles
  after a change".
- `flutter analyze` clean; `flutter test test/list test/hillclimb`: 1,406 passed.
- Wire format, cache bytes and the server's ranking: not touched.

## Left out, and why

- **#270 (compact cache snapshots), all of it.** `main`'s `ListSnapshot.version` is already 4 with
  another layout (lists and claims, job 169b), so the codec would need a version 5 and a rewrite for
  the fields added since 5 November. An older build reading a version 5 snapshot throws, drops the
  cache and overwrites it, losing offline changes not yet sent (after a downgrade; read in the code,
  not run). The codec's shared string table also undoes job 221's one-row save (#470):
  every tick would encode every row again. Its win (load at start, the first save after a load) is
  real in #270's numbers, but it changes the stored format, which the brief rules out.
- **#271 attempts 7 and 9 (rows as arrays, times as epoch micros):** the same cache format change.
- **#271 attempt 3 (keep each item's `toJson`):** on `main` already in another form (job 221's
  `ListSnapshot.encode()` keeps each row's JSON text).
- **#271 attempt 8 (fold each usual once):** superseded by #268's index, which folds once per list.
