# Job 304: CI speed, R1 and R2 of the CI report (2026-11-18)

Peter picked R1 and R2 of `lego-ci-report.md` (LR1). CI, workflows and docs only, no app code.

## What changed

- **e2e shards by measured time (R1).** `scripts/gates/e2e.sh --shard=i/n` now runs the shard's part
  of a greedy split by per-test duration. `e2e/shards.mjs` lists the suite, plans the split from
  `e2e/shard-durations.json` (the medians of the last 5 green main runs), writes
  `e2e/shard-tests.txt`, and checks Playwright's `--test-list` selection against it. Shard 1 keeps
  65 s free for the integration-lock run and the sync smoke test, and Firefox counts as one worker.
  If a test can't be named in a test list (a '›' in a title, padding, or a title path that is a
  prefix of another test's), every shard falls back to Playwright's `--shard` and logs a warning.
  `scripts/e2e-durations.sh` refreshes the durations. A spec plus `--shard` keeps Playwright's own
  split. The shard count stays at 4.
- **e2e apt cache.** The key ends in a hash of the cached packages, so a run that downloaded
  something saves a new entry. Only the packages installed at the end of setup stay in it, and the
  fallback stays on the same OS.
- **StoreKit tests in their own job (R2).** `scripts/gates/ios-storekit.sh` runs in the new
  `ios-storekit` job on macos-26. It runs on the same `native` switch as `ios` and is in `ci-ok`'s
  needs. Both gates source the build in `scripts/ios/build-for-testing.sh`. `ios.sh` runs
  RunnerTests without the StoreKit tests, as before.
- **Not done.** The shared web build: by the step timings it saves no wall time (DECISIONS, Job 304,
  item 3). R3 waits for the lead.
- Docs: `docs/CI.md` (shards, gates table, filter, Measuring, Measurements job 304), `AGENTS.md`
  (MERGE_WAIT list), and `docs/DECISIONS.md` (Job 304).

## Evidence

Wall times are in `docs/CI.md`, "Measurements (job 304, November 2026)". In short, for runs that ran
every job:

| | `ci-ok` after creation | ios job | slowest e2e job |
| --- | --- | --- | --- |
| Before (PR runs 44242102263, 44236144523, 44188358573) | 35.7, 29.3, 35.8 min | 35.2, 28.7, 33.8 | 16.4, 14.9 |
| After (#540 runs 44252828321, 44255892833, 44259795582, 44262138767) | 24.1, 28.9, 16.4, 31.5 (macOS queue) min | 20.0, 17.8, 16.0, 16.6 (ios-storekit 15.4, 21.6, 13.5, 11.9) | 14.1, 28.5 (apt), 12.2, 14.1 |

The slowest shard's Playwright time was 9.5 to 9.9 min before. After, it was 9.7 (on slow runners),
7.8 and 7.6 min. The spread between the four shards fell from 4.7 to 5.5 min to 1.0 to 3.1 min.

## How to verify

- `node --test e2e/shards.test.mjs`, `scripts/e2e-gate-test.sh`, `scripts/ci-changes-test.sh`,
  `scripts/check-gates.sh`, all in the lint gate.
- `cd e2e && node shards.mjs show 4` prints the planned estimates. It needs the stack, or
  `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` and `MAILPIT_URL` set to any value.
- `scripts/ci-ios-phases.sh <run>` splits the ios and ios-storekit jobs into phases.

## Left open

- Each native run now uses two macOS runners. In run 44262138767 both waited 14.8 min in the macOS
  queue, while other jobs' macOS runs were going.
- Runner speed varies by about ±20% per shard, and the split cannot remove that.
- The ios job's first simulator boot (4.6 to 8.6 min) is now the native critical path.
- A cache miss on a slow Ubuntu mirror still costs minutes. Both are possible follow-ups.
