one shopping day; each edits and deletes; each shows the next firing; each refuses exact duplicates and stops at

## Recommendation

**SR2 `week-map`**, runner-up **SR1 `reminder-list-sheet`**. SR2 needs 3 taps for the typical reminder and 5 for
the second Saturday one, the fewest of the compact options, and shows both Saturday reminders under Saturday as
"Day before · 20:00" (moon) and "On the day · 9:15" (sun). SR1 is 44 px more compact and the most familiar, for
one tap more each. Worth grafting onto SR2 in the build: SR3's three preset times as one-tap chips above the time
grid (not built or measured).

## Backend and scheduling the build would need (flagged only, mcp freeze)

- One row per reminder instead of one per person: shopping weekday, offset, local time, zone, language, its own
  `last_sent_on`; RLS by user and a pgTAP case.
- RPCs to add, update and delete (or set all) with the cap on the server; the old
  `set_shopping_day_reminder(p_weekdays…)` stays for old builds and writes 19:00 day-before rows.
- `shopping_day_run` must fire any local time (every 10 minutes with a catch-up window, per reminder, across DST)
  instead of only 19:00–19:29.
- "Saved after the time counts as sent", per reminder.
- On-the-day push copy „Heute ist Einkaufstag“ / "Shopping day today"; Legal reviews fields and copy.
- Migration of today's weekday rows (SR-Q5).

None of this is in the PR: no `supabase/functions`, migration, cron, RPC or push-copy change.
