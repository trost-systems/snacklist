# Job 473: add-sheet match rows read homographs as the server does

PR: https://github.com/trost-systems/snacklist/pull/748

## What was broken

Gap 1 of vmaint-20261126. On the users' build (`add-match-rows` full since 25 Nov), typed „Schäufele“ next to „Schaufel“ offered „Zusammenführen, 2× Schaufel“, and „Beeren“ next to a renamed „beer“ offered „2× beer“. The add sheet keys both sides with the device's `canonicalKeyOf`, and that had no equivalent of the server's `homograph_pick` (#536).

## What was built

- **Migration `supabase/migrations/20261126150000_catalog_homographs.sql`.**
  - `catalog_rows()` gains `homographs`: `[form, surface, canonical, category, synonym]`, one row per spelling, from `classifier_lexicon.homographs`. The catalog version covers it.
  - Answers from `catalog_delta` that carry tables also carry every homograph row (11 today).
  - `catalog_snapshots.homographs` is new and null in older snapshots, which still answer with changes.
  - The migration snapshots the current version before the definition changes. Released apps that bundle it therefore get changes, not the whole catalog.
- **Backward compatibility.** Released apps' `parseCatalogDelta` reads only version, full, terms, forms and brands, so it ignores the new key. The "you are current" answer is unchanged.
- **`supabase/classifier/client_catalog.sh`** bundles the rows as `catalogHomographs` in `app/lib/list/catalog/catalog_index.g.dart`.
- **`app/lib/list/catalog/catalog_index.dart`.** `CatalogIndex.homographs` holds them by form. A delta with homographs replaces them, one without keeps them, and a bad homograph row rejects the whole answer.
- **`app/lib/list/catalog/suggest_entries.dart`.** `canonicalKeyOf(name)` applies a literal port of `homograph_pick` and `surface_word`, where `classifier_words` applies them. `canonicalOfKey` (memory rows, key only) is unchanged.
- **Decisions.** See docs/DECISIONS.md, "Job 473".

## Results

- The new tests failed first on main: 5 failures (2 unit, 3 widget). Tomate/Tomaten passed before and after.
- `flutter test test/list`: 1,412 passed.
- `supabase test db`: all files pass. `catalog_delta.test.sql` has 9 new checks.
- **Parity with the server**, checked on the local stack with a throwaway test. `canonicalKeyOf` equals `public.canonical_key` for all 1,811 dictionary terms, synonyms and homograph names. On main's app code, 15 differed.
- `supabase/tests/suggest_parity.json` was rewritten from the stack. Only the delta answer changed.
- **Live, on the release web build** of this branch with a fresh local stack (`launch.sh --fresh`, all migrations from scratch), `journeys/classifier-homographs-dup-hint.mjs` PASSES. „Schäufele“ after Schaufel gets no merge row, and neither does „Beeren“ after a renamed „beer“. „Bier“ after „beer“ offers „Zusammenführen, 2× beer“. The same journey fails on the users' build. Evidence: `docs/screenshots/473/web-*.png` and `web-journey.log`.
- Screenshots are in `docs/screenshots/473/`. `before-main-Schaeufele.png` shows main's „2× Schaufel“, and `after-*.png` shows this branch.

## Rollout

No new flag. The fix sits under `add-match-rows`, which is already full. It reaches testers with the next green main build on TestFlight and Play internal. The migration deploys with the PR's supabase-deploy.

## Follow-ups (not done here)

- **Töpfe and Topf** get different canonical keys on the server (`topfe` and `topf`), so neither the duplicate hint nor the match rows join them. The device used to join them because it ignored the homographs. Joining two spellings of one category on a shared form changes the server's canonical rule and needs an items backfill, so it belongs to a classifier job.
- **The on-device category guess** (`guessCategory`) can now read the same homographs. The parity pins `Topf`, `To` and `Schäufele` in `suggest_parity_test.dart` stay until a job ports `classify_item_detail`'s homograph path.
