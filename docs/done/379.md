# Job 379: IH2 invite hand-off across browsers

## What was found
- On web the invite already rode in the sign-in's return link (`/?invite=<code>`) before this job. A magic link opened in another browser, or in a new tab after the first tab is gone, lands on the invite's sign-in (`/login?invite=<code>`), never on the guided start. Proven on main as it was before #657 (review 0: the same e2e passed on the pre-change build).
- #657 added the invite to the return link when `next` is also set. `LoginScreen` never gets both (`authRedirect` carries one or the other), so that code was dead. Reverted here.
- The report in Q1 (household name, then „Bestehendem Haushalt beitreten“, then the name step) was not reproduced by a browser switch. Likeliest cause, not tested: a phone without the app. The invitee opens the join link, installs the app from the store and opens it fresh; there is no deferred deep link, so the invite is lost and the guided start follows. Worth its own job (for example the join page offering to copy the code before the install).

## What stays open
- The magic link does not sign in across browsers: its PKCE verifier lives in the browser that asked for it. Browser B shows the invite's sign-in with no word that the link came from elsewhere; a person without a password needs a second email there. A `token_hash` link plus `verifyOtp`, or a message in B, is auth processing or new copy: Legal and a product call.
- `carry()` leaves the invite out of the URL when a consent `next` exists; same-browser recovery covers it (the pending invite on the device), a browser switch does not. Rare.
